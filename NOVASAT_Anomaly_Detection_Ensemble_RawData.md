# NOVASAT — Anomaly Detection Model Development: Ensemble Score + Raw Data Standard

**Scope of this doc:** the next piece of model-development work, in order — (1) a standing rule for all future models about data provenance, (2) the exact procedure for combining the existing Gaussian (EllipticEnvelope) and Isolation Forest models into one tuned probability score, (3) a repeatable checklist to apply to every model built after this one. This is the first model-development doc under the new raw-data standard; everything after "anomaly detection for compromised/hacked/defective nodes" comes after this.

---

## Part A — Standing rule going forward: raw, publicly available data

### A.1 What went wrong last time, stated precisely (not to relitigate, just to fix forward)

Track 1 Phase 4's anomaly dataset was, even after both disconnect-and-fix cycles, still **simulated telemetry generated by your own code** — real Mars simulation timing and real Phase 1/2 outputs feeding it, which was a real and correct fix at the time, but the underlying feature values (`cpu_load`, `queue_depth`, `interarrival_mean_ms`, `power_level`) were synthesized, not recorded from an actual spacecraft. That's a different, milder problem than the original fake-4-hour-Earth-orbit dataset, but it's still not raw data. Going forward, every model gets checked against this question before training starts: **could you point to the specific public source this exact value came from, unmodified in units?** If not, it's synthetic, and that needs to be stated plainly in whatever gets built, not implied to be more than it is.

### A.2 Two real public options, checked and compared — not just asserted

| | SMAP/MSL (Telemanom, Hundman et al. 2018) | ESA-ADB / OPSSAT-AD (2024–2025) |
|---|---|---|
| Source | Real NASA telemetry, SMAP satellite + MSL/Curiosity rover | Real ESA telemetry, 3 large missions + OPS-SAT CubeSat |
| Access | `wget https://s3-us-west-2.amazonaws.com/telemanom/data.zip`, labels at `github.com/khundman/telemanom` | Zenodo (DOI 10.5281/zenodo.12528696), CC BY 3.0 IGO |
| Values | **Pre-scaled to (-1, 1)** per-channel using test-set min/max — not original physical units | Real units, described as reflecting the raw telemetry actually accessible to spacecraft operations engineers, including irregular timestamps and communication gaps |
| Channel identity | Anonymized beyond a type-prefix letter (P = power, R = radiation, etc.) | Real, documented channel/subsystem structure |
| Multivariate usability | **Not usable as true multivariate data** — channels are separate, unsynchronized fragments with no shared timestamp alignment across channels | Genuinely synchronized multivariate recordings — this is the specific problem ESA-ADB was built to fix |
| Scale | 82 channels total, ~496k telemetry values, 105 labeled anomaly sequences | 224 channels, 821 control signals, 1,430 annotated events, several years of data |
| Best fit for you | Legacy benchmark, extremely well-cited, easy to cite in a paper's related-work section | Better technical fit for your actual need: a single-timestamp multivariate feature vector (matches your `cpu_load` + `queue_depth` + `power_level` simultaneous-feature structure) |

### A.3 Recommendation

**Use ESA-ADB (or its OPSSAT-AD subset) as the primary public dataset**, for one specific technical reason: your models need a real multivariate snapshot — several features observed at the same timestamp, scored together — and SMAP/MSL's unsynchronized-channel structure genuinely cannot provide that, independent of any other consideration. Using SMAP/MSL for a genuinely multivariate model would be repeating a version of the same problem you're trying to fix, just imported from someone else's dataset instead of your own synthesis. **Cite SMAP/MSL in the paper's related-work section regardless** (it's the standard reference point in this literature, already noted in the earlier related-work list), but don't build the standalone validation experiment on it.

The **OPS-SAT (OPSSAT-AD)** cut specifically is worth a second look before committing to full ESA-ADB: it's a small CubeSat mission rather than a large multi-decade spacecraft, which is a closer structural match to a small swarm of small satellites than either SMAP (one large Earth-observing satellite) or the big ESA missions in the full ESA-ADB set.

### A.4 How this reconciles with NOVASAT's own simulated data — two separate, non-merged jobs

This mirrors the original Phase 4 roadmap item, now made the standard rather than a nice-to-have:
- **NOVASAT's own simulated telemetry** trains and tests the models that actually run inside the NOVASAT simulation (live or batch) — this has to stay simulated, because there's no public dataset of "Mars orbital swarm satellite telemetry with a colluding compromised node," that scenario is specific to this project.
- **ESA-ADB / OPSSAT-AD** is a **separate, standalone validation experiment** — same modeling approach (Gaussian + Isolation Forest, same ensemble method from Part B below) trained and evaluated on real public spacecraft telemetry, with its own real schema and real labels, kept **entirely separate** from NOVASAT's synthetic schema. Do not merge the two feature sets — that reintroduces exactly the kind of mismatch/leakage problem already flagged as a reason not to do this. If the same modeling method holds up on real public data too, that's a real, independent, citable piece of evidence the approach generalizes beyond your own simulation — which is a stronger claim than either dataset alone supports.

## Part B — Combining Gaussian + Isolation Forest into one tuned probability score

### B.1 Current state (recap, not re-litigating)

Track 1 Phase 4, on the real reconnected dataset: Gaussian (EllipticEnvelope) test F1 = 0.9086 (precision 0.9703, recall 0.8542); Isolation Forest test F1 = 0.4678 (precision 0.5401, recall 0.4126). Two separate models, two separate outputs — no combined score exists yet. This is the open item from the original roadmap, being designed now.

### B.2 The core design decision — and why it's not "just average the two numbers"

Two real options. Recommending the first, but both are legitimate and the choice should be documented either way.

**Option 1 (recommended): logistic regression stacking.**
Treat each base model's **raw continuous anomaly score** — not the binary flag — as an input feature to a small logistic regression that outputs one calibrated probability.

- From `EllipticEnvelope`, use `.decision_function(X)` — continuous, roughly centered around zero, positive leaning toward inlier.
- From `IsolationForest`, use `.decision_function(X)` or `.score_samples(X)` — also continuous, but on a **different scale** than the Gaussian score (Isolation Forest's score is based on average path length in the isolation trees; the Gaussian's is a Mahalanobis-distance-derived score). **Do not average these two raw numbers directly** — they're not on comparable scales, and a naive average would silently let whichever model happens to have larger-magnitude outputs dominate the result regardless of which one is actually more accurate.
- **Standardize both scores first** (`StandardScaler`, fit on train-set scores only) before feeding them into the logistic regression. This makes the two input features comparable in scale and makes the learned coefficients interpretable (a coefficient near zero genuinely means "this model isn't contributing," not an artifact of scale mismatch).
- The logistic regression itself has exactly 3 parameters (2 weights + 1 bias) — low enough to not meaningfully overfit even on a modest validation set, and it directly gives you the "equation with tuned parameters" you asked for:
  ```
  combined_score = sigmoid(w1 · standardized_gaussian_score + w2 · standardized_iforest_score + b)
  ```

**Option 2 (simpler fallback): weighted average via grid search.**
```
combined_score = w · gaussian_probability + (1 − w) · iforest_probability
```
Grid-search `w` in `[0, 1]` (step 0.01 is plenty), pick whichever `w` maximizes F1 on the validation set. One parameter, maximally interpretable, easier to explain in a paper's methodology section — but less principled than letting a model learn the combination, and doesn't naturally handle the raw-score-scale problem the way standardization + logistic regression does (you'd need to convert each model's raw score to a calibrated probability first — e.g., via Platt scaling — before this kind of average is meaningful at all, which is extra work Option 1 gets for free).

**Recommendation: Option 1.** It's barely more code than Option 2, handles the scale-mismatch problem correctly by construction, and gives a real equation with real fitted coefficients rather than a single hand-tuned weight.

### B.3 The leakage trap — this is the part to get exactly right

This is the same category of mistake that's already been caught twice in this project (the two Phase 4 dataset disconnects) — worth being explicit about the correct procedure rather than assuming it's obvious:

1. **Fit both base models on the train set only** (`train_normal.csv`) — exactly as already done, no change.
2. **Tune each base model's own hyperparameters** (Gaussian's `support_fraction`, Isolation Forest's `contamination`) against the validation set, independently, exactly as already flagged as an open item to confirm — this has to happen and be confirmed *before* step 3, with both models' hyperparameters frozen once decided.
3. **Generate both models' raw scores on the validation set** (not train, not test) using the now-frozen base models.
4. **Fit the logistic regression meta-model on those validation-set scores against the validation-set true labels.** This is the step most likely to get leakage wrong if rushed — the meta-model's training data is the val set's *scores*, evaluated against the val set's *labels*, using base models that were already frozen in step 2. The meta-model has never seen train or test data directly.
5. **Touch the test set exactly once**, at the very end: run both frozen base models on test, standardize using the scaler fit in step 4 (not refit on test), pass through the frozen logistic regression, report the final combined F1/precision/recall.

If steps 2 and 4 get collapsed into one pass over the same validation set without care, you risk the meta-model implicitly absorbing information about the exact hyperparameter tuning decision — a subtle leakage path, worth a specific sentence in whatever writeup covers this, not left implicit.

### B.4 Evaluation — what actually counts as a real result here

Report three numbers side by side on the test set, touched once: Gaussian alone, Isolation Forest alone, combined. **The combined score only means something if it beats both individual models**, not just the weaker one. If the combined F1 lands between the two individual F1s rather than above both, that's an honest result worth reporting as-is — it would mean Isolation Forest's contribution is net-negative rather than complementary, given how far behind it already is (0.4678 vs 0.9086) — a real, informative finding either way, not something to iterate on until it looks better.

### B.5 Definition of done

- [ ] Base model hyperparameter tuning confirmed done via validation-only discipline (the already-flagged open item)
- [ ] Both raw scores standardized via a scaler fit on train only
- [ ] Logistic regression meta-model fit on validation-set scores vs. validation-set labels, base models frozen beforehand
- [ ] Final combined F1/precision/recall reported on test set, touched once
- [ ] Combined result compared honestly against both individual base models — real improvement or real non-improvement, either way reported
- [ ] Fitted equation (weights + bias) written out explicitly in whatever documentation follows this

## Part C — General model development procedure, going forward (apply to every future model)

A repeatable checklist, distilled from what's already been established the hard way across Phase 4's two disconnect cycles and the Phase 3 cold-start bug:

1. **Data provenance stated explicitly before any code is written:** real recorded data (name the exact public source and confirm access), or NOVASAT-simulated data (state this plainly, don't let it read as more than it is).
2. **Train/val/test split decided and written down before fitting anything** — which data each phase touches, and confirmation the test set gets touched exactly once.
3. **Leakage check, specifically for any multi-stage model** (base models + meta-model, or any pipeline with more than one fitted component) — trace exactly which data each fitted component saw, in order, the same way Part B.3 does above.
4. **A too-clean result is a stop-and-check signal, not a milestone** — exactly 100% accuracy, identical results across conditions expected to differ, or a suspiciously large gap between two models expected to be comparable, all get an independent check of the underlying numbers before being accepted.
5. **A too-flat or non-improving result gets reported honestly, not iterated on until it looks better** — a negative result (the ensemble doesn't beat the better base model; the public-data validation doesn't hold up as well as the simulated one) is real information, not a failure to hide.
